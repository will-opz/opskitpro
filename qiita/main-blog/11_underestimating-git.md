# 8年前の自分は Git を低く見ていた。SVN から GitOps、そして AI Workflow まで

先日、8年前に V2EX で書いた自分の返信を偶然見つけました。

当時の話題は「まだ会社で SVN を使っているのは、技術的に遅れているのか」というものでした。

その下に、当時の私はこんなことを書いていました。

> 運用担当としては、実際の業務環境では SVN と Git にそこまで差を感じない。

さらに、

> 高可用性の構成は、できるだけシンプルなほうがいい。

今読むと、少し恥ずかしいです。
ただ、当時の自分がなぜそう考えたのかは、今でも理解できます。

## 当時は SVN でも十分に見えていた

2018年ごろ、私が見ていた多くの現場では、リリースの流れはかなり単純でした。

- コードを SVN にコミットする
- Jenkins がチェックアウトする
- ビルドしてパッケージ化する
- テスト環境に出す
- 問題がなければ本番に反映する

運用担当として気にしていたのは、だいたい次のようなことでした。

- サービスが起動するか
- リリースで落ちないか
- データを失わないか
- 問題が起きたときに戻せるか

このような「人手 + 半自動化」のリリースでは、SVN でも十分に仕事は回っていました。

当時の私にとって、Git は「別のコード置き場」くらいに見えていたのです。
分散バージョン管理という説明を聞いても、日々の運用ではそこまで大きな差に見えませんでした。

## 低く見ていたのは Git ではなく、その周りに生まれる生態系だった

後から考えると、私が見誤っていたのは Git そのものではありません。

Git から広がっていった開発プロセスの変化を、ちゃんと見えていませんでした。

GitHub / GitLab、Pull Request、Code Review、CI/CD、Infrastructure as Code、GitOps。

これらがつながることで、Git は単なるバージョン管理ツールではなく、チーム開発の中心になりました。

もちろん、すべてのチームが Git の「分散」機能を毎日フル活用しているわけではありません。
しかし、Code Review なし、CI なし、変更に連動した自動デプロイなし、という状態に戻りたいチームは少ないはずです。

Git が勝ったのは、単に SVN より便利だったからではありません。
Git を中心に、現代のソフトウェア開発の標準的な流れが作られていったからだと思います。

## それでも「シンプルな構成が強い」は今も正しい

一方で、当時の自分が書いた「高可用性の構成は、できるだけシンプルなほうがいい」という考えは、今でもかなり正しいと思っています。

運用を長くやっていると、技術的に先進的であることと、事業にとって良い選択であることは別だと感じます。

Kubernetes は強力です。
でも、2〜3人の小さなチームで、事業規模もまだ大きくないなら、まずは VM やマネージドサービスで安定させるほうが現実的な場合もあります。

ClickHouse のクラスタ構成も魅力的です。
でも、今後1年で本当にデータ量が爆発するのか、先に確認したほうがいいです。

多くのシステムは、性能不足よりも、複雑すぎる構成によって壊れていきます。

良いアーキテクチャとは、いちばん新しいものではありません。
そのチームが長く維持できて、深夜の障害対応でも落ち着いて扱えるものです。

## SVN、AWS、Cloudflare、Terraform、そして AI Workflow

この十数年で、手元の道具は大きく変わりました。

最初は SVN、Jenkins、MySQL、Nginx。
その後、Git、AWS、Cloudflare、Terraform。
最近は AI Workflow、Agent、LLM、Codex のような新しい自動化ツールも日常に入ってきました。

道具は変わります。
しかし、運用で解くべき基本問題はあまり変わりません。

- 安定性
- 保守性
- コスト
- 自動化
- 障害時の判断

だからこそ、コマンドや設定だけではなく、「なぜその判断をしたのか」「何を見誤ったのか」「今でも残る原則は何か」を残していくことが大事だと感じています。

技術的負債はコードの中だけにあるわけではありません。
人間の判断の中にも残ります。

## OpsKitPro は、自分の過去の運用メモを整理する場所でもある

これまで運用の中で、たくさんの小さなスクリプト、チェックリスト、障害対応メモ、調査手順を書いてきました。

ただ、それらはサーバーの片隅、プライベートリポジトリ、ローカルメモに散らばっていました。

最近、それらを少しずつ整理して、OpsKitPro という小さなサイトにまとめています。

https://opskitpro.com

最初の目的はかなり個人的です。
自分が日常的に使う DNS、IP、Web サイト診断、Security Headers、JSON、WebSocket などの確認を、ひとつの場所にまとめたかっただけです。

ただ、もし同じように深夜に障害対応している誰かの数分を節約できるなら、それは十分に意味があると思っています。

今後の OpsKitPro は、単なるツール集ではなく、

- 過去の判断を振り返る
- 運用で使うチェックをツール化する
- 文章で背景を残す
- AI Workflow も含めて再利用できる形にする

という方向で育てていきたいです。

## おわりに

8年前の自分は、Git を低く見ていました。

でも、間違えたこと自体はそこまで悪いことではないと思っています。

エンジニアにとって本当に危ないのは、昔の判断が外れたことではありません。
昔の判断が外れたのに、それを見直さないことです。

ツールも、チームも、運用の前提も変わります。
だから、過去の自分の判断を整理し直すことには価値があります。

OpsKitPro も、その整理の延長線上にあります。

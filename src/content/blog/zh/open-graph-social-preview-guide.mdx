把辛辛苦苦做好的网页发到 X (Twitter)、Telegram 或者微信，结果出来的预览图裂开了，标题也不对，甚至连卡片都出不来——这是很多开发者都经历过的崩溃瞬间。

市面上大多数关于 Open Graph 和 Twitter Card 的教程，只停留在“怎么写 HTML 标签”这一层。但实际上，真正的生产环境里，决定分享卡片能否成功渲染的关键，往往不是代码语法，而是**爬虫的行为机制、缓存策略以及网络链路的连通性**。

本文将从工程和排障的角度，带你重新梳理 Social Preview 经常出错的核心原因，并提供一份真实可用的排查指南。

## OG 与 Twitter Card 的职责边界

要覆盖 99% 的社交平台，你只需要满足两套协议：

1. **Open Graph (OG)**：由 Facebook 主导制定，是目前应用最广的通用标准。它使用 `property` 属性（例如 `<meta property="og:title" ...>`）。Facebook、LinkedIn、WhatsApp 和 Telegram 主要依赖这套标签。
2. **Twitter Card**：X 平台的私有协议，沿用了 HTML 原生的 `name` 属性写法（例如 `<meta name="twitter:title" ...>`）。

### 自动回退机制 (Fallback)

如果 X (Twitter) 在抓取网页时，没有找到对应的 `twitter:xxx` 字段（比如缺了 `twitter:title` 或 `twitter:description`），它会**自动回退去读取同名的 `og:xxx` 字段**。

但在回退机制中，有一个致命的例外：**`twitter:card` 没有回退项**。

如果你希望在 X 上展示一张漂亮的大图预览卡片，你必须显式在页面中声明：
```html
<meta name="twitter:card" content="summary_large_image">
```
如果没有这行代码，不管你的 `og:image` 写得多完美，X 最终可能只会展示一个纯文本的小卡片，甚至完全没有预览。

## 为什么卡片经常出不来：抓取链路诊断

### 1. 爬虫不执行 JavaScript
Facebook、X、Telegram 和 WhatsApp 的抓取行为均为**服务端爬虫**，它们不执行页面的 JavaScript。

如果你的网页是一个纯客户端渲染的 SPA（比如原生的 React 或 Vue），并且依赖客户端的 JS 在挂载后动态向 `<head>` 注入 `og:image`，那么爬虫抓取到的将是一个空空如也的网页头部。你的 `og:` 标签必须直接存在于服务端返回的**原始 HTML** 中（通过 SSR、SSG 或边缘网关注入）。

### 2. 图片绝对不能用相对路径
图片 URL 必须使用**绝对路径** (`https://...`)。

```html
<!-- 错误做法 ❌ -->
<meta property="og:image" content="/images/share.jpg">

<!-- 正确做法 ✅ -->
<meta property="og:image" content="https://example.com/images/share.jpg">
```

Facebook 官方文档明令禁止使用相对路径。而如果你在 Telegram 里用了相对路径，爬虫会直接报错。
**那为什么有时候用了相对路径，Telegram 还是能抓到图？**
这不是因为它支持了相对路径，而是因为 Telegram 抓取 `og:image` 失败后，触发了“降级兜底逻辑”——它会暴力扫描网页的正文，随便挑一张“看起来够大”的图来充数。这会导致抓出来的图完全不可控。

### 3. 不要使用会发生跳转的图片链接
避免把 `og:image` 放在一个 301 或 302 重定向的链接后面。很多社交平台的爬虫（尤其是 Telegram）并不会主动跟随图片的跳转链条。一旦遇到跳转，爬虫可能会直接放弃加载。请务必使用直接返回图片真实字节流的直链。

## 缓存为什么导致“明明改了还是旧图”

当你更新了 `og:image`，重新部署了代码，满怀期待地把链接发给朋友，结果发现卡片依然顽固地展示着上个月的旧图。

社交平台为了节省带宽，会在他们的服务器上对元数据进行非常强烈的缓存：
- **Facebook**：具有较强的缓存机制。你可以使用官方的 [Sharing Debugger](https://developers.facebook.com/tools/debug/) 强制刮取新数据。
- **X (Twitter)**：具备持久的缓存策略。**X 官方已经在 2022 年下线了 Card Validator 的预览和刷新功能**，现在你无法通过官方工具手动清空推特的抓取缓存。
- **Telegram / WhatsApp**：没有官方文档说明过期时间，通常极长。

### 强制刷新缓存的解法
既然无法手动清理缓存，最稳妥的做法就是“欺骗”爬虫，让它们认为这是一个全新的链接。

**解决方案**：给图片 URL 追加一个基于文件内容的查询参数（Hash）。
```html
<!-- 爬虫会认为这是一张新图片，并立即重新抓取 -->
<meta property="og:image" content="https://example.com/share.jpg?v=a1b2c3d4">
```
注意，**不要直接使用部署的时间戳**。如果图片内容没有变，仅仅因为重新部署就导致时间戳变化，会触发各个平台不必要的疯狂重抓。应该使用图片真实内容的 Hash（比如存储层的 ETag），保证只有图片真换了，URL 才会变。

## “标签写对了，但爬虫真的能访问到吗？”

这是排障时最容易出现的思维盲区。开发者看着审查元素里的 `og:image` 发呆，确信自己写了绝对路径，但分享出去卡片依然是白板。

这种时候，排障的重点应该从 HTML 转移到网络边界：

1. **防火墙拦截 (Cloudflare Bot Fight Mode)**：你的 WAF 是不是防爬虫防得太狠了？社交平台的抓取机器人有自己独特的 User-Agent（如 `facebookexternalhit`, `Twitterbot`, `TelegramBot`）。如果防火墙直接给它们返回了 403 拦截，或者弹出了五秒盾，卡片注定失败。
2. **`robots.txt` 限制**：你的 `robots.txt` 是否禁用了 `/images/` 目录？部分遵守规则的爬虫会因此拒绝拉取封面。
3. **响应头 Content-Type**：如果你的服务器给图片返回了 `application/octet-stream` 而不是 `image/jpeg`，WhatsApp 这样的平台会直接丢弃该图片。
4. **图片体积和格式**：各平台对图片体积有不同的隐形限制。过大的图片，或者现代的 WebP / 动态 GIF 格式，在不同客户端和抓取链路上表现极不稳定（容易直接被加载失败或抛弃）。最安全的选择依然是高压缩比的 JPEG 或 PNG。

## Next.js Metadata API 配置参考

如果你在使用 Next.js App Router，它原生的 Metadata API 能够非常优雅地帮你自动生成并映射这些标签：

```typescript
import type { Metadata } from 'next'

export const metadata: Metadata = {
  title: '你的页面标题',
  description: '你的页面描述内容。',
  openGraph: {
    title: '你的页面标题',
    description: '你的页面描述内容。',
    url: 'https://example.com',
    siteName: '站点名称',
    images: [
      {
        url: 'https://example.com/og-image.jpg?v=hash123',
        width: 1200,
        height: 630,
      },
    ],
    locale: 'zh_CN',
    type: 'website',
  },
  twitter: {
    card: 'summary_large_image', // 极其关键，没有这一行推特不显示大图
    title: '你的页面标题',
    description: '你的页面描述内容。',
    images: ['https://example.com/og-image.jpg?v=hash123'],
  },
}
```

## 生产环境上线前 Checklist

下一次准备发布重要活动页之前，请务必对着这份列表检查一遍：

- [ ] 运行 `curl -s https://your-site.com | grep "og:image"` 是否能看到标签？（验证 SSR 是否生效）
- [ ] `og:image` 是否为 `https://...` 开头的绝对路径？
- [ ] 运行 `curl -I https://your-site.com/image.jpg`，是否直接返回了 `HTTP 200` 且 `Content-Type: image/jpeg`？（确保无跳转）
- [ ] 封面图体积是否已进行高压缩，以确保跨平台的广泛兼容性？
- [ ] 是否显式声明了 `<meta name="twitter:card" content="summary_large_image">`？
- [ ] WAF、防火墙和防爬策略是否放行了主流社交媒体的 Bot？

社交卡片不是玄学，而是一次完整的网络抓取与解析过程。只要跳出纯粹的 HTML 语法视角，从网络链路的角度去审视爬虫的每一个步骤，你就能彻底解决预览失败的问题。

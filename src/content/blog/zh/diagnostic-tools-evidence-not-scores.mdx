## 简单评分的问题

一个单一分数很让人安心。

它能快速给出答案，适合放在仪表盘里，也能把一堆复杂的诊断结果包装得很干净。

但在真实的 SRE 工作里，**没有证据支撑的分数很容易被误用**。

如果一个网站拿到了较低的安全分数，真正失败的到底是什么？

- 是证书过期了？
- 是域名和证书不匹配？
- 是缺少 HSTS？
- 还是探针看到的是 CDN 边缘节点，而不是源站？

如果一个网站拿到了很高的分数，这是否意味着源站也是健康的？

还是只能说明公网边缘节点响应得很干净？

当 CDN、反向代理或托管边缘节点负责终止 TLS，并隐藏了源站行为时，这个区别尤其重要。

所以，OpsKitPro 正在把诊断工具推向一个简单原则：

**每一个结论，都应该能回溯到产生它的证据。**

## 先有证据，再有判断

网站事故很少只表现为一个孤立信号。

用户可能反馈“网站打不开”，但公网域名仍然可以正常解析。

CDN 可能返回 522，但源站进程其实还在运行。

浏览器里 HTTPS 看起来正常，但被观测到的证书可能只代表公网 CDN 边缘节点，并不一定代表背后的源站配置。

在这种情况下，工具不应该直接跳到最终评分。

它应该展示一条推理链：

- 检查了什么
- 这次检查是从哪里执行的
- 实际观察到了什么原始信号
- 从这个信号中得出了什么诊断结论
- 可能原因或下一步应该检查哪一层
- 用户应该如何验证修复结果

这就是“装饰性评分”和“诊断报告”的区别。

## 观测点很重要

同一个目标，从不同位置看，结果可能完全不同。

浏览器看到的是来自用户设备的连接。

Cloudflare 看到的是边缘节点上的请求。

OpsKitPro Website Check 看到的是来自 OpsKitPro 服务端探针的目标状态。

源站服务器只能看到真正穿过边缘节点或代理层之后到达自己的流量。

如果这些视角没有明确标注，就会让结果变得误导。

例如，一个公网 HTTPS 检查可能观察到 Cloudflare 边缘节点的证书。这个信息有价值，但它并不能自动证明 Cloudflare 背后的源站证书也是健康的。

一次来自公网解析器的 DNS 查询，可以说明几个公共 resolver 之间的结果是否一致，但它不能证明所有企业网络、移动网络或本地 resolver 都看到同样的答案。

这就是为什么每一个诊断结果都应该保留它的测量上下文。

没有观测点，一个技术上正确的结果，也可能在运维判断上产生误导。

## 一个分数无法告诉你到底哪一层坏了

考虑一个很常见的生产架构：

```text
用户
  ↓
CDN / 反向代理
  ↓
源站服务器
```

从用户浏览器看，HTTPS 可能完全正常，因为 CDN 展示了一张有效的公网证书。

从公网诊断探针看，也可能是同样的结果：CDN 边缘节点返回了有效证书、现代 TLS 协议和正常的 HTTP 响应。

但这并不能证明源站层也同样健康。

- 源站可能使用另一张证书。
- 源站可能只允许 CDN 访问。
- 源站可能有更严格的 TLS 配置。
- 源站可能在 strict TLS 模式下失败，即使公网边缘节点看起来完全正常。

一个单一分数很容易掩盖这个区别。

证据优先的报告应该更精确地说明：

> TLS 是在公网 CDN 边缘节点上被观测到的。这些诊断结果描述的是公网探针看到的证书和协议，并不一定代表 CDN 背后的源站配置。

这个限制不是报告的缺点。

它是真相的一部分。

## 一个有用的诊断结论应该回答四个问题

在 OpsKitPro Website Check 里，我们希望每个 finding 都尽量回答四个问题。

第一：**观察到的证据是什么？**

它可以是状态码、DNS 记录、证书日期、响应头、重定向链、CDN 线索、TLS 协议、加密套件，或者 resolver 返回结果。

第二：**为什么它重要？**

缺少 Content-Security-Policy 是安全加固问题。

TLS 域名匹配失败是连接信任问题。

Cloudflare 522 指向的是 Cloudflare 与源站之间的连接超时，而不是浏览器渲染问题。

第三：**可能原因是什么，或者下一步应该检查哪一层？**

工具应该区分“源站不可达”“证书即将过期”“缺少安全响应头”，而不是把所有问题都压缩成一个抽象分数。

第四：**用户应该如何验证下一步？**

一个诊断报告不应该只是描述失败，还应该提示下一步检查方向。

例如：

- 如果 DNS 解析失败，检查权威 DNS 记录和 resolver 行为。
- 如果 TLS 域名匹配失败，检查 SAN 和实际请求的 hostname。
- 如果检测到 CDN，需要区分公网边缘行为和源站行为。
- 如果响应缺少安全头，检查这些 header 是应该由应用、代理还是 CDN 层添加。

一个有用的诊断结论，不应该假装自己已经找到了最终根因。

它应该帮助操作者选择下一步该检查哪一层。

## 分数仍然有用，但只能作为摘要

这并不是说分数本身没有价值。

分数可以帮助用户快速浏览一份很长的报告。

它可以显示系统是否在逐步改善。

它也可以让报告更容易被扫描和排序。

问题出现在：**分数变成了产品本身**。

一个好的诊断分数，应该像是通往证据的索引。

如果 TLS 部分出现 warning，用户应该能看到这个问题到底来自：

- 证书过期
- 域名匹配
- 证书链授权
- OCSP stapled response 是否存在
- 遗留协议暴露面
- CDN 边缘终止上下文
- 未知的探测结果

如果没有这些拆解，分数看起来可能很精确，但实际隐藏了不确定性。

在诊断系统里，**unknown 不等于 pass**。

**not verified 也不等于 failed**。

这些区别很重要。

## 这如何影响 OpsKitPro 的设计

OpsKitPro Website Check 会把 DNS、HTTP、CDN、TLS 和安全响应头信号转化为结构化报告，并生成有优先级的 findings。

它的目标不是替代监控系统、日志平台或云厂商仪表盘。

它的目标是缩短第一轮排障时间。

对于一个公网网站来说，第一批问题通常很简单，但很关键：

- 域名是否能解析？
- HTTP 是否可达？
- 响应是否经过 CDN？
- 在当前观测端点上，TLS 是否健康？
- 关键安全响应头是否存在？
- 这个结果来自用户设备，还是来自 OpsKitPro 探针？
- 下一步应该检查什么？

很多时间就浪费在这第一轮判断上。

一个能够解释证据的工具，可以帮助操作者在打开五个不同仪表盘之前，先判断应该优先检查哪一层。

## 为什么 OpsKitPro 不把黑盒评分当最终结论

OpsKitPro 不会把所有诊断结果最终压缩成一个 A-F 总分。

这是有意为之。

评分可以作为摘要，但它也可能隐藏测量边界。

例如：

- 没有检测到 OCSP stapled response，并不自动意味着证书无效。
- TLS 探针失败可能是因为超时，但这并不能证明目标不安全。
- CDN 边缘节点可能展示了很强的公网 TLS 配置，但源站配置仍然不在公网探针的观测范围内。
- 遗留协议探测可能因为连接重置而返回 unknown，而不是明确的协议拒绝。

诊断工具不应该把这些情况压平，制造一种虚假的确定性。

它应该保留这些状态之间的区别：

- pass
- fail
- warning
- informational context
- unknown

这没有单一评分那么炫。

但当有人真的在修生产问题时，它更有用。

## 尝试证据优先的诊断流程

打开 [Website Check](/zh/tools/website-check)，输入用户实际访问的 hostname，并先查看报告中显示的观测点。

然后把诊断结果当成一条链来看：

```text
观测点
  → 原始证据
  → 诊断结论
  → 边界限制
  → 可能原因或下一步检查层级
  → 验证步骤
```

这条链才是工具真正的价值。

如果存在分数，它也只应该是最上层的标签。

真正让你能采取行动的，是证据。
